# Known limitations (honest list)

1. **The companion app is required.** A pure Obsidian plugin cannot send Termux's RUN_COMMAND intent (the sender must hold `com.termux.permission.RUN_COMMAND` in its own manifest), so the small companion app is mandatory. The [Termux:Widget](https://github.com/termux/termux-widget) variant was dropped because it needed a manual tap per operation. Running `~/.config/native-git-bridge/runner.sh` in Termux by hand remains a recovery path.
2. **Companion transport verified on-device; still device-specific caveats.** The thin companion app (`companion/`) is complete and CI-buildable (`.github/workflows/build-companion.yml`), but two things still need a real device: (a) that Obsidian's Android WebView dispatches `window.open("nativegitbridge://…")`; a synthetic-anchor-click fallback is included; (b) the RUN_COMMAND permission grant + `allow-external-apps` flow. The APK cannot be compiled in this environment (no Android SDK); use the CI workflow or Android Studio.
3. **This environment cannot run Android/Termux.** The runner script is exercised end-to-end in a Linux sandbox against a real git repo with sparse checkout, identical git semantics, but Android storage permissions, scoped-storage quirks (e.g. `mv` atomicity on FUSE shared storage) and widget behavior need on-device QA. On some Android FUSE mounts `mv` within one directory is atomic enough, but this is asserted, not proven here; the plugin tolerates partially-written results by retrying JSON parse on next poll.
4. **Wi-Fi-only and battery-aware sync**: Obsidian plugins have no stable public API for network type or battery level; `navigator.connection` / `navigator.getBattery` exist in some WebViews but are not guaranteed. Implemented as best-effort, default-off, and clearly labeled.
5. **[Version History Diff](https://github.com/kometenstaub/obsidian-version-history-diff) has no public provider API** (uses [obsidian-git](https://github.com/Vinzent03/obsidian-git)'s private plugin API). This plugin therefore ships its OWN history and diff views (the repository history panel and the diff pane, rendered by this repository's own code since 0.6.2, in the same visual style); an upstream adapter PR remains an option. We will not monkey-patch another plugin's internals. One known nuance of our diff pane: a pure rename can display as an addition, because the runner limits the diff pathspec to the file's new path. The conflict-resolution pane writes REMAINING (unresolved) blocks back in an Obsidian-safe marker form (`-<<<<<<<` / `-=======` / `->>>>>>>`): the standard markers render a note as headings and nested blockquotes in Obsidian's editor. Both forms are parsed; git is unaffected (the unmerged state lives in the index). A desktop editor will, however, show the dashed markers on a file half-resolved on the phone. Conflict resolution is per **block**, not per hunk or per line, and only for files that decode as text; binary conflicts can only be resolved whole-file (keep local / keep remote). Staging below file level arrived in 0.6.2 and works on a hunk or on individually picked lines, but only for text files that produce a unified diff: a binary file can still only be staged whole, and hunks past the diff size budget are not rendered, so they cannot be picked until the budget is raised. A patch that no longer matches the file is refused rather than fuzzed into place. Restoring one block from the file-history panel applies only when the current file still contains that block verbatim (either the pre-commit or the post-commit side); if the file drifted the plugin refuses rather than guessing where the block belongs, and the whole-file restore is the way out. A rename is visible as a move only once it is staged: git detects renames by comparing the index, so an unstaged move is reported by git itself as a deletion plus an untracked file, and `git status --find-renames` does not change that. Whitespace glyphs are a rendering pass over the shown text, so copying from the diff or the conflict pane copies the glyphs, not the original whitespace. The status panel's auto-refresh is a plain interval, not a file watcher: Obsidian gives no reliable signal for changes made outside the app on Android, so the interval is opt-in and off by default (every tick wakes Termux).
6. **Foreground-session commands on Android ≥ 10** may require Termux's "Draw over other apps" permission; the runner therefore always runs as a **background task** (`.shortcuts/tasks/`), which is unaffected.
7. **Finding a moved or unpaired vault relies on a filesystem scan.** Relocation and self-pairing look for `runtime/profile.json` and `runtime/claim.json` under `/storage/emulated/0`, `~/storage/shared` and `/sdcard`, at most nine levels deep, and only on a run that has no other work (or when a profile is broken). A vault outside those roots, deeper than that, or on external storage Termux cannot read will not be found; re-run the installer with its path instead. The scan matches `*/plugins/native-git-bridge/runtime/*`, so a custom Obsidian config directory is fine, but a vault the runner cannot read at all is invisible to it.
8. **Self-pairing trusts the device, not the claim.** A `claim.json` is honoured only for a directory that is a git work tree of its own, under the scan roots, younger than 15 minutes, and it never supplies its own token (Termux generates one). Anything with write access to shared storage can still cause an empty profile to be created for a repository that is already there; it cannot choose the token, the path is one the user already has, and nothing is fetched or pushed by pairing alone. Removing the profile file undoes it.
9. **Per-repository credentials are configured, not enforced.** The installer sets `credential.helper store --file=…` or `core.sshCommand` **locally** for the repository it configures. A global helper configured earlier still applies to repositories that have no local one, so two vaults on the same host can share an account until you give the second one its own credential file. The runner never touches credentials. GitHub OAuth through `gh` (`pkg install gh`, device flow, then `gh auth setup-git`) works and is documented in [setup.md](setup.md), but the installer does not configure it: gh writes a **global** helper and answers for whichever account is currently active, so it cannot separate two accounts per vault. Git Credential Manager has no Android build.
10. **Custom pane colours are flat hex, and only for the four/two variables named in the settings.** Obsidian's colour picker has no alpha, so a custom colour is opaque where the built-in default is a translucent tint over the theme background; switching the toggle back off restores the defaults. Most of those defaults are translucent, with one deliberate exception: the deleted-character highlight is a solid `#AA1414` with white text, because the translucent red it replaced washed out against the red row on a phone, which is exactly where the changed characters are hardest to find. Colours are per theme (light / dark) and are stored in `data.json`, so they are shared across devices like the other cosmetic preferences. The conflict pane tints whole lines and therefore has no character-highlight colour to configure.
11. **Two things are still shown in a modal rather than a pane.** "Show the file as it was at this commit" (the eye button in the file-history panel) opens a read-only text preview, and a binary file at a commit reports itself in a notice. A whole-file preview is not a diff, so it has no line numbers, no wrapping toggle and no colours; every actual diff and every history list is a pane.
12. **A clone cannot be interrupted once git is running.** The runner has no cancellation point inside a git command, so cancelling or timing out a `clone-into-vault` stops the plugin waiting, not the clone. The design compensates rather than pretends: the repository is moved into the vault only after the clone succeeds, so the vault is either untouched or complete. A cancelled clone may still finish in the background and the next *Status* will show the repository.
13. **Bootstrap only covers the parts that carry no secret.** `init-repo`, `set-remote` and `clone-into-vault` never see a credential: a URL with a password in it is refused, cloning a private repository needs the credential helper or SSH key to be set up in Termux first (`docs/setup.md`), and a first commit needs `user.name` / `user.email` there too. The plugin reports exactly which of those is missing, but it cannot fix any of them for you.
14. **A re-clone leaves the previous repository on disk until you deal with it.** That is deliberate — it may hold commits that exist nowhere else — but it means a vault of a few thousand files can carry a few hundred megabytes it did not have before. The plugin reminds you once a day and can delete it in one tap; nothing deletes it on its own, and the reminder is device-local, so another device syncing the same vault never nags about a copy it does not have.
15. **stdout/stderr size**: results carry full outputs in files (no intent size limits), but the plugin truncates displayed output at 100 KB with a "see runner.log" hint.
16. **A lightweight repository trades offline reach for disk, and says so up front.** Shallow history and partial clone (Settings → *Repository footprint*, runner v14+) are per-device choices with per-device costs. On a shallow repository the history panels reach only the commits that stayed, restoring a file from an older commit is not possible on that device, and enabling it clears that device's reflog — kept, it would pin the old commits and the cut would free nothing. On a partial clone, file content the device never fetched arrives from the remote on demand: *Show again (remove sparse exclusion)* and old file versions need the network, and offline they fail with git's own "unable to fetch" error rather than a tailored one. Space actually returns with *Clean up repository storage*; on a device whose git predates 2.42 the already-downloaded content of a partial clone cannot be shed and stays until a newer git runs the maintenance. Disabling either is one large download, and disabling partial clone is refused if the content cannot all be brought back — the repository is never left claiming completeness it does not have.
17. **The status panel draws a limited number of rows per group.** git reports a fully untracked directory as a single entry and the panel expands it into real rows, so a folder of a few thousand new files meant a few thousand rows redrawn on every render: measured on the device, the spinner took about two seconds to appear with such a folder open and none when it was collapsed. All four groups can be long at the same time, so there is a budget, 30 rows by default and configurable per device. Where it applies depends on the layout, because the two layouts can say different things about what was left out. **List layout**: one page per group, with a control at the end of the group. **Tree layout**: one page per folder, with a control inside each folder that stopped short — a single control at the end of a tree could not say which folders were cut — plus a ceiling of ten pages per group, because a page in each of fifty folders is the cost this exists to bound. Either control adds another page on tap and reads `30/2415 files • Tap for more`, naming its unit because a folder row is a row and not a file. A folder row counts as a row, which is why the line states rows and files separately rather than as a ratio. The group's own count is unaffected: it counts files, so it always states the true total, and staging or deleting a folder acts on all of it rather than on what is drawn. Nothing is hidden from git; the rows are simply not built until asked for.
